# Drum Pattern Generator — Design Spec

**Date:** 2026-07-29
**Status:** Approved for planning

## 1. Обзор

Веб-платформа для барабанщиков, которая генерирует барабанные паттерны заданной
длины и размера из рудиментов, отрисовывает их нотами и даёт прослушать —
кроссплатформенно (не завязано на движки ОС).

**Область MVP:** малый барабан (snare / practice pad). Модель данных
проектируется мульти-поверхностной (задел на бочку/томы/хай-хэт), но MVP рисует
на одной нотной линии.

**Движок генерации MVP:** детерминированный бэктрекинг-солвер с гарантией
корректной аппликатуры. LLM-ассист — фаза 2.

## 2. Музыкально-теоретический фундамент

### Длительности нот

Длительность хранится как рациональная доля целой ноты (`Fraction`), не float —
чтобы `1/4 + 1/8 == 3/8` было точным равенством.

| Нота | Доля | Триоль |
|---|---|---|
| Целая | 1 | — |
| Половинная | 1/2 | — |
| Четверть | 1/4 | 1/6 |
| Восьмая | 1/8 | 1/12 |
| Шестнадцатая | 1/16 | 1/24 |
| Тридцать вторая | 1/32 | — |

Точка увеличивает длительность на половину (♩. = 1/4 + 1/8 = 3/8).
**Триоли обязательны** — они важны для рудиментов; `Fraction` покрывает их
знаменателями 6/12/24.

### Размер (метр)

`TimeSignature(num, den)` → длина такта = `num × (1/den)` целой ноты.
- Простые размеры: 2/4, 3/4, 4/4.
- Сложные размеры: 6/8 (группировка 3+3), 9/8, 12/8. Группировка влияет на
  рёбра/лиги и на расстановку метрических акцентов; простые и сложные
  обрабатываются по-разному при группировке.

### Ключевой инвариант такта

Сумма длительностей всех нот в такте **точно равна** длине такта. Это формальная
запись требования «нота вписывается в размерность фразы и такта». Генератор
обязан его соблюдать, валидатор — проверять.

## 3. Модель данных

Домен — **Pydantic-модели** (`BaseModel`), а не dataclasses/чистый Python. Причина:
Pydantic даёт готовые JSON-схемы (`model_json_schema()`), которые в фазе 2
напрямую скармливаются LLM как structured output, а также единообразную
валидацию домена и DTO. Это осознанная зависимость домена от Pydantic ради
упрощения будущего внедрения LLM.

Длительность: `Fraction` оборачивается через `Annotated` + кастомный
`field_validator`/сериализатор, чтобы Pydantic корректно (де)сериализовал
`Fraction` в строку вида `"1/12"` в JSON и обратно.

`hand`, `articulation`, `surface`, `accent_mode` — строковые `Enum`
(автоматически попадают в JSON-схему как перечисления — удобно для LLM).

```python
class Stroke(BaseModel):
    duration: FractionField          # длительность (Fraction, сериализуется как "1/12")
    hand: Hand                        # L | R
    accent: bool = False              # акцент (>)
    articulation: Articulation = Articulation.NORMAL   # MVP: normal
    surface: Surface = Surface.SNARE  # задел на мульти-поверхность

class Bar(BaseModel):
    time_sig: TimeSignature
    strokes: list[Stroke]             # инвариант суммы длительностей (model_validator)

class Phrase(BaseModel):
    time_sig: TimeSignature
    tempo_bpm: int
    subdivision: FractionField
    accent_mode: AccentMode
    bars: list[Bar]
```

Инвариант такта (§2) реализуется как `model_validator(mode="after")` на `Bar`,
инварианты правил аппликатуры (§5) держим в отдельном валидаторе-модуле (§8), а
не в самой модели, чтобы можно было строить промежуточные невалидные состояния во
время поиска в генераторе.

## 4. Каталог рудиментов

За основу — канонический стандарт **PAS 40 International Drum Rudiments**,
4 группы. Каждый рудимент — шаблон: последовательность
`(относительная длительность, рука, акцент, артикуляция)`, укладываемая на сетку
такта. Каталог хранится как данные (JSON / `rudiments.py`), с флагами:
- `mvp: bool` — входит ли в MVP-генерацию;
- `violates_core_rules: bool` — нарушает ли встроенно правила (см. §5).

### Группы

- **A. Roll rudiments:** Single Stroke Roll (`R L R L`), Double Stroke Roll /
  диддлы (`R R L L`), Triple Stroke Roll, Multiple Bounce (buzz),
  Five/Six/Seven/Nine/…/Seventeen Stroke Roll.
- **B. Diddle rudiments:** Single Paradiddle (`R L R R  L R L L`), Double
  Paradiddle, Triple Paradiddle, Paradiddle-diddle (`R L R R L L`).
- **C. Flam rudiments** (фаза 2): Flam, Flam Tap, Flamacue, Flam Paradiddle,
  Flam Accent, Pataflafla, Swiss Army Triplet, Inverted Flam Tap, Flam Drag.
  Флэм = тихий форшлаг одной рукой перед основной нотой другой (`lR`).
- **D. Drag rudiments** (фаза 2): Drag, Single/Double Drag Tap, Lesson 25,
  Single/Double Dragadiddle, Drag Paradiddle #1/#2, Single/Double Ratamacue.
  Драг = двойной форшлаг (`ll`) перед основной нотой.

### MVP-подмножество

Роллы (кроме нарушающих правила, напр. Triple Stroke Roll) + диддлы/парадиддлы.
Флэмы, драги и любые форшлаг-ноты (grace notes) — фаза 2 (упрощает нотацию).

## 5. Правила аппликатуры (жёсткие ограничения)

Проверяются **только по основным нотам**. Форшлаг-ноты (grace notes флэмов и
драгов) из проверки исключены — правила смотрят на поток основных атак, форшлаги
считаются орнаментом.

1. **Нет акцента сразу после неакцента той же рукой.** Запрещена пара соседних
   ударов `x, y`, где `hand(x) == hand(y)`, `accent(x) == False`,
   `accent(y) == True`. Пример `rR` (тихая правая → громкая правая).
2. **Нет трёх ударов одной рукой подряд.** Запрещено
   `hand(i) == hand(i+1) == hand(i+2)`. Это исключает из MVP-генерации
   рудименты со встроенным нарушением (Triple Stroke Roll и т.п.) — они
   помечаются `violates_core_rules: true`.

## 6. Детерминированный генератор

### Вход

`{ time_sig, num_bars, min_subdivision, tempo_bpm, accent_mode, seed? }`

- `min_subdivision` — мелкость (напр. 1/16 или 1/12 для триолей).
- `accent_mode` — **опция пользователя**:
  - `rudiment` — акценты по шаблону рудимента (как учат);
  - `metric` — акценты по сильным долям такта (музыкальнее);
  - `both` — рудимент задаёт базу, метрические доли усиливают.
- `seed` — воспроизводимость и разнообразие.

### Алгоритм (бэктрекинг, такт за тактом)

1. **Сетка такта:** длина такта режется на ячейки по `min_subdivision`; длина
   каждого рудимента выражена в этих ячейках.
2. **Состояние поиска:** позиция в такте, последние 2 руки, последний удар
   (рука + акцент) — переносится через границы тактов.
3. **Шаг:** выбор рудимента из MVP-каталога, влезающего в остаток такта, в одной
   из двух ориентаций (зеркалирование аппликатуры R↔L). Рудименты каталога
   предварительно провалидированы на внутреннее соблюдение правил.
4. **Проверка шва:** правила §5 между последними ударами и первыми ударами
   нового рудимента; не прошло — другая ориентация / другой рудимент.
5. **Бэктрек** при тупике. `seed` перемешивает порядок кандидатов.

### Гарантия

На выходе — всегда валидный паттерн, либо явная ошибка «невозможно при данных
параметрах» (напр. размер не бьётся на выбранную мелкость). Бэктрекинг
предпочтён жадному алгоритму: правило шва может завести жадность в тупик к концу
такта; бэктрекинг находит решение, если оно существует. MVP-каталог небольшой →
поиск быстрый.

## 7. Архитектура

Monorepo: `backend/` + `frontend/`.

### Backend (Python, uv)

Слоёная структура. Единственная внешняя зависимость домена — Pydantic (см. §3).

```
domain/      Pydantic-модели: Stroke, Bar, Phrase, TimeSignature, enums, FractionField
catalog/     рудименты как данные + флаги (mvp, violates_core_rules)
generator/   бэктрекинг-солвер
validator/   проверка 2 правил аппликатуры
api/         FastAPI
```

Сериализация в JSON DTO — это `phrase.model_dump(mode="json")` самой Pydantic-модели,
отдельный слой `serializer/` не нужен. FastAPI использует те же модели домена как
схемы запроса/ответа: одна модель = домен + DTO + JSON-схема для LLM.

**API:**
- `POST /generate` — тело
  `{time_sig, num_bars, min_subdivision, tempo_bpm, accent_mode, seed?}`
  → ответ `Phrase` JSON (такты; ноты с длительностью/рукой/акцентом).
- `GET /rudiments` — каталог (справка + задел под будущий фильтр).

### Frontend (Vue 3 + Vite + TypeScript)

```
GenerationForm.vue   форма параметров → POST /generate
ScoreView.vue        отрисовка Phrase через VexFlow (аппликатура R/L, акценты >)
PlayerControls.vue   play/stop, темп, счёт-затакт
lib/audio.ts         Tone.js: планировщик Transport, снейр-звук
lib/score.ts         маппинг Phrase JSON → примитивы VexFlow
```

**Поток данных:** форма → `POST /generate` → `Phrase` JSON → одновременно
(1) рендер нот VexFlow, (2) расписание `Tone.Transport`. Акцент = выше velocity.
Старт воспроизведения требует user gesture (ограничение Web Audio) — учитывается
в UI.

**Звук снейра в MVP:** синтез через Tone.js (`NoiseSynth` + фильтр), без внешних
сэмплов — полностью самодостаточно и кроссплатформенно (Web Audio доступен
везде). Реальный сэмпл легко подменить позже.

## 8. Тулинг и тестирование

**Python:** `uv`, `ruff` (strict lint + format), `pyright` (strict),
`pytest` + `hypothesis`.

**Стратегия — ядро проверяем свойствами, а не примерами:**
- **Domain:** арифметика `Fraction`, инвариант такта.
- **Validator:** ловит `rR` и `RRR` на подготовленных кейсах.
- **Generator (property-based):** для широкого диапазона входов выход **всегда**
  проходит валидатор И сумма длительностей точна; отдельно — корректная ошибка
  на невозможных параметрах.
- **Catalog:** каждый MVP-рудимент внутренне проходит правила; помеченные
  `violates_core_rules` реально исключены из генерации.
- **API:** FastAPI TestClient на `/generate` и `/rudiments`.
- **Frontend:** Vitest на маппинге `Phrase → VexFlow` и на аудио-расписании
  (чистые функции, без реального звука).

Property-тесты дают гарантию: генератор физически не может выдать невалидную
аппликатуру.

## 9. Отложено на фазу 2

- LLM-ассист (выбор рудиментов / «характер» фразы; валидатор чинит нарушения).
- Флэмы, драги, форшлаг-ноты и их нотация.
- Пользовательский фильтр разрешённых рудиментов.
- Мульти-поверхностная оркестровка (бочка, томы, хай-хэт).
- Реальные сэмплы вместо синтеза.

## 10. Открытые допущения

- Список рудиментов не является пользовательским контролем в MVP: генератор сам
  берёт рудименты из MVP-каталога.
